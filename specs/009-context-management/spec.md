# HuiCode Context Management Spec

## Background

HuiCode 已经具备多轮 Agent Loop、工具调用、工具结果回灌、Rich TUI、权限系统和 MCP 工具接入。随着用户长时间对话、反复读取文件、运行命令或调用 MCP 工具，历史消息会不断增长，尤其是工具结果会快速占用上下文窗口。当前已有简单的大工具结果落盘能力，但缺少统一的预算估算、整体历史压缩、手动触发和失败熔断机制。

本章目标是在有限 Token 预算内保持 HuiCode 长时间可用。策略分两层：第一层在每次请求前预防性压缩大工具结果；第二层在整体历史逼近窗口上限时生成结构化摘要，压缩较早历史并保留近期原文。

## Goals

- 让 HuiCode 在长会话中不容易因为上下文过大而请求失败。
- 优先压缩工具结果，尽量保留用户原始消息，不用摘要改写用户表达。
- 在自动压缩之外提供用户手动压缩入口。
- 让模型在压缩后清楚知道摘要不是文件事实来源，需要细节时必须重新读取。
- 在摘要失败时可恢复、可停止，不进入反复压缩的死循环。
- 让压缩过程在 TUI 中可观察，方便用户理解上下文被怎样处理。

## Functional Requirements

- F1: 每次 API 请求前，HuiCode 必须先执行轻量预防压缩，检查即将发送的历史中是否存在过大的工具结果。
- F2: 单个工具结果超过阈值时，HuiCode 必须把完整结果保存到磁盘，并在对话历史中只保留结果摘要、预览和可重新定位的文件路径。
- F3: 单条消息或同一轮工具结果合计超过阈值时，HuiCode 必须优先压缩占用最大的工具结果，直到该轮工具结果降到预算内或已经没有可压缩项。
- F4: 轻量压缩不得摘要或改写用户原始消息；用户消息应尽量按原文保留。
- F5: HuiCode 必须维护近似 Token 预算，用上一次 API usage 作为锚点，对后续增量使用字符数近似估算。
- F6: 每次 API 请求前，轻量预防完成后，HuiCode 必须判断整体历史是否逼近上下文窗口上限。
- F7: 自动整体压缩必须保留 13K Token 安全余量；用户手动压缩时安全余量收窄到 3K Token。
- F8: 触发整体压缩时，HuiCode 必须保留近期原文，从尾部按近似 Token 往回保留约 1 万 Token，并且至少保留最近 5 条消息。
- F9: 整体压缩必须只摘要较早消息，近期保留区内的消息不得被摘要改写。
- F10: 整体摘要必须使用结构化格式，至少包含：当前任务、用户目标与约束、已完成动作、重要发现、已修改或涉及的文件、关键工具结果、待办事项、风险与未知点。
- F11: 摘要请求必须明确禁止模型调用任何工具。
- F12: 摘要请求必须要求模型先写分析草稿再写正式摘要，但 HuiCode 只能保留正式摘要，不能把草稿写入对话历史。
- F13: 整体压缩成功后，HuiCode 必须在历史中插入一条清晰的压缩边界消息，提醒模型摘要只是导航信息；如果需要文件细节、命令输出或工具完整结果，必须重新读取或重新调用工具，不能照摘要脑补。
- F14: 用户必须能通过 TUI 命令手动触发整体压缩，并能看到压缩是否执行、跳过或失败。
- F15: 连续摘要失败达到 3 次后，HuiCode 必须熔断自动整体压缩，避免每轮请求前重复失败；熔断后仍允许轻量工具结果压缩。
- F16: 摘要失败或熔断不得清空对话历史，不得丢失未压缩的用户消息和近期消息。
- F17: 压缩事件必须在 TUI 中显示简洁状态，包括轻量压缩落盘数量、整体摘要是否触发、估算释放量或失败原因。
- F18: 压缩后的历史必须继续兼容 OpenAI 和 Anthropic 工具调用序列要求，不能破坏 tool_use 与 tool_result 的对应关系。
- F19: 压缩应覆盖本地工具和 MCP 工具返回的大结果，不能只处理内置文件工具。
- F20: 用户清空会话时，HuiCode 必须同时重置上下文管理状态，例如估算锚点、摘要失败计数和压缩摘要状态。

## Non-Functional Requirements

- N1: 本章使用近似 Token 估算即可，不要求接入精确 tokenizer。
- N2: 压缩逻辑应优先稳定和可恢复，不能为了省 Token 牺牲协议合法性。
- N3: 落盘内容必须保存在 workspace 内，不能逃逸项目目录。
- N4: 压缩提示和边界消息必须使用中文，并尽量简洁。
- N5: 自动压缩不应明显打断普通短会话；只有接近预算时才触发重量兜底。
- N6: 压缩状态和配置摘要不得泄露 API key、headers、MCP env 或其他 secret。
- N7: 测试必须覆盖真实用户长会话形态，而不只覆盖单个内部函数。

## Out of Scope

- 不实现精确 tokenizer。
- 不做基于机器学习的摘要策略优化。
- 不实现跨会话长期记忆。
- 不实现项目指令文件或自动记忆加载。
- 不实现用户交互式选择哪些消息被压缩。
- 不把摘要文件上传到远端存储。
- 不做对落盘工具结果的自动垃圾回收策略。
- 不改变现有权限系统、MCP 协议能力或工具权限模型。

## Acceptance Criteria

- AC1: 当单个工具结果超过阈值时，下一次发送给模型的历史只包含摘要、预览和落盘路径，完整结果存在 workspace 内文件中。
- AC2: 当同一轮多个工具结果合计超过阈值时，HuiCode 会优先压缩最大的结果，并保留较小结果内联。
- AC3: 工具结果压缩后，TUI 显示落盘数量和路径摘要。
- AC4: 用户原始消息在轻量压缩后仍保持原文。
- AC5: 长历史接近窗口上限时，API 请求前自动触发整体摘要压缩，且保留最近约 1 万 Token 或至少 5 条消息的原文。
- AC6: 手动压缩命令可触发整体压缩，并使用比自动压缩更窄的安全余量。
- AC7: 整体摘要包含固定结构部分，并替代较早历史进入后续请求。
- AC8: 整体摘要过程中模型不能调用工具；如果摘要模型返回工具调用，压缩视为失败并保留原历史。
- AC9: 摘要分析草稿不会进入对话历史，历史中只保留正式摘要和边界消息。
- AC10: 压缩边界消息明确要求模型需要细节时重新读取或重新调用工具，不能凭摘要脑补。
- AC11: 连续 3 次摘要失败后，自动整体压缩熔断；后续请求不会反复尝试整体压缩，但仍能继续轻量压缩工具结果。
- AC12: 摘要失败、熔断或跳过压缩时，对话历史不会被清空，最近消息和用户原文仍可用。
- AC13: 压缩后的 OpenAI 请求历史和 Anthropic 请求历史仍满足各自工具调用序列要求。
- AC14: 本地工具和 MCP 工具的大结果都能被轻量压缩处理。
- AC15: `/clear` 后上下文管理状态被重置。
- AC16: `/config` 或其他状态输出能展示上下文管理摘要信息，但不泄露 secret。
- AC17: README 说明上下文管理策略、手动压缩命令、落盘位置和限制。
- AC18: 自动测试覆盖轻量压缩、整体摘要、手动触发、失败熔断、协议序列兼容和 TUI 输出。
- AC19: 验收报告记录 tmux E2E 是否执行；如果当前 Windows 环境没有 tmux，必须写明不可用原因。
