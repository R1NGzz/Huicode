# HuiCode 系统提示词完善 Spec

## Background

HuiCode 已有结构化系统提示模块，但当前提示内容较简略，且部分文件在 Windows 终端显示中出现中文编码损坏。用户提供了多张参考截图，展示了更细的系统提示分层：身份、系统约束、任务执行、谨慎操作、工具使用、语气风格、文本输出。本次目标是在不改变 Agent Loop、Provider、工具执行机制的前提下，完善 HuiCode 的系统提示词，让模型更稳定地遵守工作方式和输出风格。

## Goals

- 让 HuiCode 的系统提示更接近成熟 Coding Agent 的行为约束。
- 强化“安全优先、不要编造、专用工具优先、编辑前先读、谨慎副作用操作”等规则。
- 保持现有七个固定模块结构，不引入新运行机制。
- 修复系统提示相关文件中的中文可读性问题。

## Functional Requirements

- F1: 身份模块应明确 HuiCode 是运行在终端中的 AI 编程助手，能协助代码任务、调试、重构、解释代码和运行命令。
- F2: 身份模块应包含基础安全边界，要求不要引入注入、XSS、SQL 注入等常见安全漏洞，优先输出安全、正确的代码。
- F3: 系统约束模块应明确工具调用之外的文本都会展示给用户，回复可使用 Markdown，用户不知道工具调用细节，不能提及内部 system-reminder。
- F4: 系统约束模块应明确用户可见 URL 才能使用，不要生成或猜测 URL，并将 hook 或系统事件视为用户发起的上下文。
- F5: 任务执行模块应指导模型处理模糊需求、探索性问题、用户建议、修改任务、错误信息和测试结果，避免过度实现和擅自做额外工作。
- F6: 谨慎操作模块应区分低风险本地操作和高风险/破坏性操作，并要求对删除、重置、发布、推送、批量修改等操作先确认。
- F7: 工具使用模块应强化专用工具优先：读文件用 Read，编辑用 Edit，创建用 Write，查找文件用 Find，搜索内容用 Search，命令只在必要时用 Bash。
- F8: 工具使用模块应结合 HuiCode 当前已有工具能力，不要求不存在的 Task、Agent、MCP 或 ToolSearch 真实能力。
- F9: 语气风格模块应要求除非用户明确要求，否则不使用 emoji；回复简洁；引用具体代码位置时使用 `file_path:line_number` 风格。
- F10: 文本输出模块应要求面向用户只输出有用沟通，少讲内部权衡；工具调用前后用简短句子更新；最终总结控制在一到两句话，任务简单时直接回答。
- F11: 完善后的提示词不应泄露内部 prompt 标签、缓存策略细节或不可见系统消息。
- F12: 现有动态环境注入、Plan Mode/Do Mode 注入频率、Provider 序列化和缓存 usage 行为应保持不变。

## Non-Functional Requirements

- N1: 提示词内容应为 UTF-8 中文，源码阅读时不应出现乱码。
- N2: 变更应保持小范围，主要集中在系统提示模块和相关测试。
- N3: 单元测试应覆盖新增关键规则，防止未来误删。
- N4: 不应引入新的第三方依赖。

## Out of Scope

- 不实现新的工具、权限系统、确认交互或 Agent 子任务能力。
- 不接入真实 MCP、TaskCreate、子 Agent 或 ToolSearch。
- 不改变 Provider 请求协议、Agent Loop 停止条件或 TUI 渲染机制。
- 不根据截图逐字照搬其他项目名称；所有内容应适配 HuiCode。

## Acceptance Criteria

- AC1: 运行 prompt 模块测试时，身份、安全、系统约束、任务执行、谨慎操作、工具使用、语气风格、文本输出的关键规则均被覆盖。
- AC2: 构建 PromptBundle 后，稳定模块仍按既定优先级输出，动态环境和模式指令仍单独注入。
- AC3: 工具提示不引用 HuiCode 不存在的工具能力。
- AC4: 全量测试通过。
- AC5: README 或验收报告记录本次提示词完善范围和未实现能力边界。
