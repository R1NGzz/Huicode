# Agent Team 需求规格

## 背景

HuiCode 已具备子 Agent、后台任务和 Worktree 隔离能力，但现有子 Agent 仍以一次性委派为主，缺少长期团队、共享任务、成员直连通信和统一集成机制。复杂任务中的拆分、依赖协调、进度同步与成果合并仍主要依赖主 Agent 临时转述，容易造成上下文膨胀和协作瓶颈。

本章将主 Agent 扩展为 Team Lead。Lead 可以建立长期存在的团队，为成员分配独立工作目录，通过共享任务清单和邮箱组织协作，并在专用集成环境中汇总成果。团队成员完成当前任务后进入空闲状态，后续可以恢复原上下文继续工作。

## 目标

- 支持创建、恢复和管理长期存在的 Agent 团队。
- 支持多个成员在独立 Worktree 中并行工作。
- 让团队成员通过共享任务清单和点对点消息直接协作。
- 为需要审批的成员建立不可绕过的计划审批闸门。
- 支持强隔离终端后端与轻量同进程后端，并明确展示实际选择。
- 在不污染用户当前工作区的前提下完成成员分支集成。
- 提供双重开启的 coordinator 模式，使 Lead 专注协调、审批与集成。

## 功能需求

### F1 团队生命周期与持久化

- 用户可以创建、查看、恢复、关闭和删除团队。
- 每个团队具有唯一名称、负责人、成员花名册、创建时间、当前状态和持久化位置。
- 团队信息保存在用户目录下按团队名隔离的位置，HuiCode 重启后可以恢复。
- 团队名称必须经过安全校验，不得造成路径遍历、目录冲突或覆盖其他团队。
- 关闭团队不得自动丢弃仍有变更、未读消息或未完成任务的成员状态。

### F2 成员花名册与状态

- 每个成员记录唯一名称、角色、工作目录、工作分支、期望后端、实际后端、审批要求和运行状态。
- 成员至少支持启动中、工作中、等待审批、空闲、失败、已停止等可观察状态。
- 同一团队内不得存在重名成员。
- 单个成员启动或运行失败不得导致整个团队或其他成员退出。

### F3 运行后端选择

- 成员支持独立终端实例和同进程协程两类运行后端。
- 自动选择后端时按 `tmux`、Windows Terminal 分屏、同进程协程的顺序探测。
- 启动成员时必须向 Lead 展示实际选中的后端，不得静默切换。
- 显式要求终端后端但当前环境不可用时，成员启动必须失败并给出原因，不得自动降级为协程。
- 独立终端实例与协程实例都必须保持各自的会话状态、权限状态和 Token 用量。

### F4 成员工作区隔离

- 每个团队成员都必须拥有独立 Worktree 和独立分支，包括只读角色和协程后端成员。
- 成员的文件读取、写入、搜索、命令执行和路径相关缓存必须绑定自己的绝对工作目录。
- 成员修改不得直接出现在 Lead 的当前工作区，也不得直接覆盖其他成员文件。
- Worktree 创建失败时成员不得退回主工作区继续执行。
- 成员状态中必须能查看对应 Worktree 和分支。

### F5 团队协作工具作用域

- 团队 Lead 可以使用团队管理、任务管理、消息、审批、终止和集成相关能力。
- 团队成员可以使用共享任务和成员消息能力，但不能获得仅属于 Lead 的审批、集成或团队管理能力。
- 普通主会话和非团队子 Agent 不得看到或调用团队协作工具。
- 工具可见范围必须由运行身份决定，不能仅依赖提示词约束。
- 团队成员不得通过团队工具无限派生新的团队或普通子 Agent。

### F6 共享任务清单

- 团队可以持久化共享任务，支持新增、查询、更新、认领、完成和失败标记。
- 任务至少记录标识、标题、说明、状态、负责人、依赖项、结果摘要和更新时间。
- 未完成依赖存在时，任务必须保持阻塞，不得进入执行状态。
- 系统必须拒绝不存在的依赖、自依赖和可检测到的循环依赖。
- 多个成员同时更新任务时不得产生部分写入或无提示覆盖。
- Lead 和成员都能读取当前任务状态，但只有符合身份与任务归属规则的操作才能修改任务。

### F7 名称注册表与邮箱通信

- 点对点消息必须先通过团队名称注册表解析收件人，再写入对应邮箱。
- 支持单个成员消息和团队广播。
- 每条消息至少包含发件人、收件范围、正文、摘要、时间戳、已读状态和协议类型。
- 消息默认未读；读取后可标记已读，并保留历史。
- 邮箱写入使用锁文件保证并发安全；获取失败时重试，超过配置期限的锁可视为过期。
- 独立终端后端收到新消息时，系统还必须尝试唤醒对应终端实例。
- 唤醒失败只影响即时通知，不得丢失已落盘消息。

### F8 结构化协作消息

- 团队消息支持普通文本以及任务分配、计划申请、计划决定、进度、完成、空闲、唤醒和停止等结构化协议。
- 结构化消息必须包含可关联的请求或任务标识，避免把不同任务的回复错误配对。
- 未知或损坏的协议消息应被隔离并报告，不得阻塞整个邮箱读取。
- 普通自然语言消息不得被误解析为审批决定或其他控制指令。

### F9 人工审批成员

- 标记为需要审批的成员必须先向 Lead 提交结构化计划申请。
- Lead 只能通过专用的结构化审批能力，按请求标识批准或驳回计划；普通聊天回复不能改变审批状态。
- 在收到匹配的批准前，成员不得调用写文件、改文件或其他有副作用的工具。
- 驳回必须携带反馈，成员可以据此修改计划并重新申请。
- 过期、重复或请求标识不匹配的审批决定不得解除执行闸门。
- 审批状态必须持久化，以便成员或 HuiCode 重启后继续等待正确决定。

### F10 成员空闲与上下文恢复

- 成员在模型自然停止且当前任务处理完毕后，应标记为空闲并通知 Lead。
- 空闲成员保留可恢复的对话、任务、权限和工作目录状态。
- Lead 后续向空闲成员发送消息时，系统应从磁盘恢复该成员上下文并继续执行，而不是创建一个同名新成员。
- 恢复过程必须遵守现有会话安全规则，包括损坏记录处理、工具调用配对和上下文预算控制。
- 恢复失败时应将成员标为失败并向 Lead 报告，不得静默从空白上下文重新开始。

### F11 Lead 编排能力

- Lead 可以把用户目标拆成带依赖关系的共享任务，并为任务分派或调整成员。
- Lead 可以查看团队、成员、任务、邮箱、审批和集成状态。
- Lead 可以向成员单发或广播消息，并可以停止指定成员或整个团队。
- Lead 必须能识别成员失败、任务阻塞和审批等待，并采取重新分配、反馈或终止等动作。
- 团队协作状态变化应通过异步事件反馈到界面，不得依赖轮询式自然语言询问。

### F12 成果集成与冲突处理

- 成员成果不得直接合并到用户当前工作区或当前检出分支。
- 系统必须创建专用集成分支和集成 Worktree，在其中按任务依赖和完成状态汇总成员分支。
- 只有工作分支状态可确认且成果已提交的成员才能进入自动集成。
- 发生冲突时，Lead 可以委派专门成员在集成环境中尝试解决并执行验证。
- 冲突无法解决或验证失败时，系统必须中止本次集成并清理未完成的集成状态，用户当前工作区保持不变。
- 全部合并与验证成功后，才可以把集成结果快进或合并到目标分支。
- 若目标分支自团队启动以来发生变化，系统必须重新校验可合并性，不得覆盖新的提交。

### F13 Coordinator 模式

- Coordinator 模式只有在配置能力开关和用户环境变量同时启用时才生效。
- 只开启其中任意一把锁时，系统必须保持普通 Lead 模式并明确显示未满足的条件。
- Coordinator 模式下，Lead 不得使用直接写文件和编辑文件的工具。
- Coordinator 模式保留读类工具、团队管理、成员终止、消息、审批和集成能力。
- 为完成 Git 检查与集成而保留的命令能力必须限制在协调和 Git 集成用途，不得成为绕过文件写入限制的通道。
- 当前模式必须显示在界面状态中，并在每轮工具选择时持续生效。

### F14 配置与状态展示

- 用户可以配置团队能力开关、默认后端、终端后端要求、邮箱锁重试与过期时间、成员并发上限和 coordinator 能力开关。
- 配置错误应在启动或团队创建阶段集中报告，不得延迟到成员执行后才失败。
- 界面应展示团队名、Lead 模式、成员数量、各成员状态与后端、任务进度、待审批数量和集成状态。
- 后端选择、审批等待、消息投递、成员空闲、成员恢复和集成结果都应有简洁可辨识的事件反馈。

### F15 安全停止与清理

- 停止成员时必须先停止其运行后端，再更新持久化状态。
- 删除团队前必须检查活动成员、未完成任务、未读消息、未集成成果以及受保护 Worktree。
- 存在受保护状态时默认拒绝删除，并说明需要处理的项目。
- 自动清理不得删除含未提交修改、未集成提交或无法确认归属的 Worktree。
- 独立成员、邮箱或集成清理失败不得损坏其他团队的数据。

## 非功能需求

### N1 隔离性

- 成员之间的消息、权限、上下文、Token 用量、文件缓存和工作目录不得串线。
- 团队协作不得修改 HuiCode 进程的全局当前目录。

### N2 并发安全

- 任务清单、名称注册表、邮箱和团队元数据的并发更新必须具备原子性或等价保护。
- 进程中断后最多丢失正在写入的一条记录，已有有效记录仍可恢复。

### N3 可靠性

- 单个成员、后端、邮箱或集成操作失败不得使主会话崩溃。
- 可恢复操作应尽量幂等；重复消息、重复审批和重复状态更新不得产生重复副作用。

### N4 安全性

- 所有团队名、成员名、任务标识、分支名和持久化路径都必须在使用前验证。
- Coordinator 限制、审批闸门和工具作用域必须由程序执行，不能只依赖模型遵守提示词。
- 集成失败和团队删除采用默认拒绝、保留成果的策略。

### N5 可诊断性

- 关键状态转换应记录可关联的团队、成员、任务或请求标识。
- 错误应指出失败阶段、受影响对象和可采取的恢复动作，且不得泄露密钥或敏感环境变量。

### N6 可移植性

- 同进程协程后端应能在 HuiCode 支持的平台上工作。
- 终端后端的能力探测和不可用错误应适配 Windows、Linux 和 macOS 的差异。

### N7 可测试性

- 后端探测、任务依赖、邮箱锁、审批闸门、成员恢复和集成失败回滚应可在临时目录和临时 Git 仓库中独立验证。
- 自动化测试不得依赖用户真实团队目录、真实终端会话或远程 Git 仓库。

## 不在本章范围

- 跨机器、跨网络节点的分布式团队。
- 成员之间逐 Token 的实时流式通信。
- 条件依赖、资源依赖、投票等复杂任务约束。
- 自动决定业务层面的最佳团队规模和角色组合。
- Worktree 成果的远程推送、Pull Request 创建和代码托管平台集成。
- 多团队之间的共享任务或共享邮箱。
- 后台团队任务的无限期跨版本兼容迁移。

## 验收标准

### AC1 团队创建与恢复

创建一个合法命名的团队后，可查看负责人、花名册和持久化位置；重启 HuiCode 后可恢复相同团队和状态。非法或冲突名称在写入前被拒绝。（覆盖 F1、F2）

### AC2 后端选择透明

在不同能力探测结果下，自动模式依次选择 tmux、Windows Terminal、协程并展示实际结果；显式要求终端而环境不可用时启动失败且不降级。（覆盖 F3、F14）

### AC3 全成员 Worktree 隔离

同时启动至少两个不同后端或角色的成员后，每个成员都拥有不同 Worktree 和分支；成员修改互不覆盖且不出现在用户当前工作区，创建失败时不会退回主目录执行。（覆盖 F4）

### AC4 团队工具作用域

Lead、团队成员、普通主会话和普通子 Agent 分别只能看到其身份允许的工具；后两者无法发现或调用团队协作工具，成员也无法调用 Lead 专属审批与集成能力。（覆盖 F5）

### AC5 共享任务并发与依赖

Lead 建立含依赖的任务后，前置任务未完成时后续任务保持阻塞；非法依赖被拒绝。两个成员并发认领或更新任务时，最终状态一致且不存在部分写入或无提示覆盖。（覆盖 F6）

### AC6 邮箱直连与广播

成员可以按名称互发消息，Lead 可以广播；消息落盘后包含规定字段并默认未读。并发写入通过锁安全完成，过期锁可恢复，终端唤醒失败时消息仍可读取。（覆盖 F7、F8）

### AC7 审批闸门

需要审批的成员提交计划后进入等待状态，在收到匹配的结构化批准前无法执行副作用工具；自然语言批准、错误请求标识和重复决定均无效。驳回反馈可用于重新规划并再次申请。（覆盖 F8、F9）

### AC8 空闲与继续指派

成员完成任务后标记空闲并通知 Lead；重启或释放运行实例后，向该成员发送新任务会从持久化上下文恢复，而不是创建同名新成员。损坏状态会明确失败，不会从空白历史冒充恢复。（覆盖 F10、F11）

### AC9 Lead 编排与故障隔离

Lead 可以建立任务依赖、分派成员、查看状态、发送消息和停止成员。单个成员或后端失败时，其他成员与主会话继续运行，Lead 能看到失败并重新分配任务。（覆盖 F2、F11）

### AC10 安全集成

多个成员提交成果后，系统在独立集成 Worktree 中按依赖汇总并验证。成功后才更新目标分支；冲突无法解决、验证失败或目标分支变化时中止集成，用户当前工作区和原目标分支不被破坏。（覆盖 F12）

### AC11 Coordinator 双重开关

仅配置开关或仅环境变量开启时仍为普通模式；两者同时开启后显示 coordinator 状态，Lead 看不到直接写改工具，非 Git 协调用途的命令不能绕过限制，同时仍能读取、派人、审批、发消息、停止成员和集成成果。（覆盖 F13、F14）

### AC12 停止与删除保护

停止成员会先终止后端再记录状态；团队存在活动成员、未完成任务、未读消息、未集成成果或受保护 Worktree 时默认拒绝删除。清理失败不会影响其他团队。（覆盖 F15）

### AC13 回归验证

现有聊天、工具、Agent Loop、权限、MCP、上下文、记忆、Slash Command、Skill、Hook、子 Agent 和 Worktree 功能继续通过自动化测试。（验证 N1、N3、N7）
