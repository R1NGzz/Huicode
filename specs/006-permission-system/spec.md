# HuiCode 五层权限系统 Spec

## Background

HuiCode 已经具备工具系统和 Agent Loop，模型可以读写文件、修改文件、执行命令、查找文件和搜索代码。当前工具层已有基础 workspace 路径约束，但还缺少完整权限体系：危险命令硬拦截、可配置规则、多档权限模式、人在回路确认，以及权限拒绝后的 Agent Loop 恢复策略。本章目标是在保持现有工具能力的基础上，为 HuiCode 增加一套五层防御权限系统。

## Goals

- 在工具执行前拦截明确危险操作，降低误操作风险。
- 将文件操作限制在项目目录内，并防止路径或符号链接逃逸。
- 允许用户通过规则配置控制特定工具调用的放行或拦截。
- 支持整体权限模式切换，用于从严格到放行的不同信任等级。
- 对规则无法明确判断的操作引入用户确认，并支持本次、本会话、永久三种放行范围。
- 权限拒绝时不终止 Agent Loop，而是把结构化拒绝结果回灌给模型，让模型调整策略。

## Functional Requirements

- F1: HuiCode 必须在工具执行前进行权限检查，检查结果决定该工具调用是否执行。
- F2: 危险操作黑名单必须优先于所有配置和模式，命中后直接拒绝，不能通过用户规则或权限模式放开。
- F3: 黑名单应覆盖常见高危命令或命令片段，例如递归强删、强制重置、磁盘格式化、权限破坏、批量覆盖或破坏系统目录等。
- F4: 文件路径沙箱必须限制读写改查相关路径只能位于当前项目 workspace 内。
- F5: 路径沙箱必须先解析绝对路径和符号链接，再判断是否在 workspace 内，防止通过 `..`、绝对路径或符号链接逃逸。
- F6: 权限系统应支持按“工具名(模式)”声明规则，例如 `Bash(git *)`、`Read(src/**/*.py)`、`Edit(README.md)`。
- F7: 每条规则的结果只能是 `allow` 或 `deny`。
- F8: 规则匹配应支持精确匹配和 glob 匹配。
- F9: 规则文件应分为用户级、项目级、本地级三层，越靠近项目优先级越高；本地级高于项目级，项目级高于用户级。
- F10: 会话内临时规则应高于三层 YAML 规则。
- F11: 权限模式应支持至少三档：严格、默认、放行；模式作为整体策略覆盖具体规则未命中的默认行为。
- F12: 规则明确命中时，应按规则结果放行或拒绝；规则未明确命中时，应根据当前权限模式决定是拒绝、询问用户还是放行。
- F13: 人在回路确认应在规则未明确命中且模式需要确认时触发，向用户展示工具名、关键参数、风险摘要和可选决策。
- F14: 用户确认应支持三种放行范围：仅本次、本会话、永久。
- F15: “仅本次”只影响当前工具调用；“本会话”应生成会话级临时规则；“永久”应写入合适的持久规则层。
- F16: 用户拒绝或超时未确认时，工具调用应返回结构化权限拒绝结果。
- F17: 权限拒绝结果应回灌进对话历史，Agent Loop 不应因为单次权限拒绝而崩溃或终止。
- F18: TUI 应能展示权限确认请求和权限拒绝摘要，让用户理解发生了什么。
- F19: 权限模式应能通过配置或 CLI/TUI 命令查看和切换。
- F20: 权限配置解析失败时，应给出清晰错误，不应静默放行。

## Non-Functional Requirements

- N1: 黑名单规则应保守、可测试，并且不可被普通配置覆盖。
- N2: 权限检查应发生在任何副作用工具执行之前。
- N3: 规则配置不应泄露 API key 或其他敏感配置内容。
- N4: 权限拒绝和确认流程应保持对模型友好，返回结构化错误，避免只给自然语言报错。
- N5: 变更应保持现有 Provider、SSE、PromptBundle 和基础 Agent Loop 行为兼容。
- N6: 单元测试应覆盖黑名单、路径沙箱、规则优先级、权限模式、人在回路和 Agent Loop 回灌。

## Out of Scope

- 不限制网络请求。
- 不实现 CPU、内存、磁盘、进程数等资源配额。
- 不实现完整审计日志系统。
- 不实现多用户权限隔离。
- 不实现操作系统级容器沙箱。
- 不把提示词规则当作安全边界；安全边界必须由代码执行。

## Acceptance Criteria

- AC1: 命中危险黑名单的 Bash 调用在任何权限模式和任何 allow 规则下都被拒绝。
- AC2: 通过 `..`、绝对路径或符号链接指向 workspace 外的文件操作都会被拒绝。
- AC3: 用户级、项目级、本地级、会话级规则按优先级正确覆盖。
- AC4: `工具名(模式)` 规则能按精确匹配和 glob 匹配对工具调用返回 allow 或 deny。
- AC5: 严格、默认、放行三档模式对未命中规则的工具调用产生不同可观察行为。
- AC6: 规则未命中且需要确认时，TUI 展示确认信息，并能处理本次、本会话、永久放行和拒绝。
- AC7: 权限拒绝会作为结构化工具结果回灌到 Agent Loop，模型可继续下一轮而不是进程崩溃。
- AC8: 配置解析失败时启动或加载阶段给出明确错误，并且不会默认放行。
- AC9: 全量单元测试和编译检查通过。
