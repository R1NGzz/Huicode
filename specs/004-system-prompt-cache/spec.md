# HuiCode 结构化系统提示与缓存策略规格说明

## 背景

HuiCode 当前已经具备流式对话、工具系统、Agent Loop、Plan Mode、Markdown 渲染和基础 CLI 交互能力。模型能调用工具完成任务，但全局行为约束仍比较粗糙：稳定身份、工具使用约定、代码规范、安全边界、任务模式和输出风格没有被系统化组织，也没有区分稳定提示与动态环境信息。

在真实使用中，模型行为质量很依赖系统提示的结构和重复强化程度。稳定指令适合长期复用并进入缓存通道，以减少延迟和成本；环境信息、会话级开关、临时补充指令则会频繁变化，应以不会污染稳定缓存的方式注入。本阶段要把 HuiCode 的系统提示升级为结构化、可组合、可缓存、可观测的提示层，让模型更稳定地遵守“优先用专用工具”“编辑前先读”“按任务模式行动”等核心约定。

## 目标

- 将全局指令拆成职责清晰的模块，并按优先级稳定拼装。
- 区分稳定提示、工具描述、动态环境信息和会话级临时指令，避免变化内容污染稳定缓存。
- 在全局指令和工具描述中双重强化关键工具使用规则。
- 支持运行中注入带特殊标签的补充指令，使其作为系统级上下文生效，而不是被当作用户提问回复。
- 让 Plan Mode 等会话级开关按轮次注入不同强度的指令，兼顾遵守率、成本和上下文占用。
- 解析并展示或记录供应商返回的缓存命中信息，便于确认缓存策略是否生效。
- 准备一组典型人工对比场景，用于评估新提示层对模型行为质量的影响。

## 功能需求

- F1: HuiCode 应将系统提示拆成固定模块，至少包括身份、系统约束、任务模式、动作执行、工具使用、语气风格、文本输出和环境信息。
- F2: 固定模块应按明确优先级拼装，默认顺序为：身份、系统约束、任务模式、动作执行、工具使用、语气风格、文本输出，最后接环境信息。
- F3: HuiCode 应预留可选模块位置，至少包括自定义指令、已激活的 Skill 和长期记忆，并且这些模块排在固定模块之后。
- F4: 模块之间应以清晰分隔呈现，避免不同职责的指令混在同一段中。
- F5: 稳定指令应与动态内容区分开；稳定内容可复用，动态环境信息和对话历史按轮次变化。
- F6: 工具描述应被视为稳定内容的一部分，在供应商支持时可进入可缓存通道。
- F7: 环境信息应包含当前工作目录、平台/终端相关信息、当前时间、当前任务模式和可用能力摘要等动态上下文。
- F8: 动态环境信息应作为系统级补充上下文注入，不能被模型当成用户消息直接回答。
- F9: 运行中补充指令应使用带特殊标签的消息形式，明确标记来源、用途和有效范围。
- F10: 补充指令不得改变真实用户消息文本，也不得污染可缓存的稳定系统提示。
- F11: HuiCode 应在全局指令中强化关键规则，包括优先使用专用工具、编辑前必须先读取相关文件、不要臆造工具结果、遵守 workspace 边界。
- F12: HuiCode 应在对应工具描述中再次强化工具级关键规则，使模型在选择工具时也能看到约束。
- F13: Plan Mode 下应注入只读计划相关指令，要求模型先分析、只使用读类工具、不执行副作用动作。
- F14: `/do` 或执行模式下应注入执行相关指令，要求模型参考最近计划、按步骤行动、必要时使用工具验证。
- F15: 会话级开关的指令应支持按轮次控制注入强度：首轮完整注入，间隔轮次重复关键约束，其余轮次使用精简提示。
- F16: 指令注入频率应可预测，避免每轮重复过长提示导致上下文膨胀。
- F17: Provider 请求应能携带系统级提示、动态补充上下文、对话历史和工具描述，并保持 OpenAI 兼容协议与 Anthropic 兼容协议都可用。
- F18: 当供应商返回缓存创建、缓存读取或缓存命中相关字段时，HuiCode 应解析这些字段并纳入 usage 事件或可观测输出。
- F19: 当供应商不返回缓存字段时，HuiCode 应保持正常对话，不把缺失缓存字段视为错误。
- F20: `/verbose` 或等价的可观测方式应能让用户看到缓存相关统计，且不得泄露 API key。
- F21: 新提示层不应破坏现有 Agent Loop、多工具调用、Plan Mode、thinking 回传、Markdown 渲染和工具结果回灌。
- F22: 新提示层应提供一组人工对比场景，覆盖入口文件分析、编辑前读取、Plan Mode 只读规划、工具优先使用、错误工具结果修正和输出风格稳定性。
- F23: 本阶段不应加载项目指令文件、不应实现自动记忆、不应接入真实 MCP，也不应做自动化评估系统。

## 非功能需求

- N1: 项目继续遵循 AGENT.md：使用 Python，实现说明和代码注释使用中文。
- N2: 系统提示模块应便于后续插入、禁用或调整优先级，而不需要大范围修改现有 Agent Loop。
- N3: 稳定提示和动态提示的边界应清晰，避免缓存命中不稳定或把临时信息长期保留。
- N4: 指令内容应简洁但明确，避免过度膨胀上下文。
- N5: 缓存统计、usage 输出和错误摘要不得包含 API key、完整配置文件内容或其他敏感信息。
- N6: 新能力应有单元测试覆盖，并通过完整测试和编译检查。
- N7: 对不支持缓存控制或缓存字段的供应商，应优雅降级。

## 范围外

- 加载项目级指令文件，例如仓库内自定义说明文件。
- 自动长期记忆、记忆总结或记忆检索。
- 真实 MCP 工具或 MCP 资源接入。
- 自动化评估框架、批量跑分或模型行为评分系统。
- 权限确认系统、上下文压缩系统或工具沙箱。
- 修改 LLM 供应商之外的外部计费策略。

## 验收标准

- AC1: 发起模型请求时，系统提示包含七个固定模块，且顺序符合身份、系统约束、任务模式、动作执行、工具使用、语气风格、文本输出、环境信息。
- AC2: 模块之间有清晰分隔，固定模块和可选模块不会混在同一段中。
- AC3: 自定义指令、已激活 Skill、长期记忆作为可选模块位置存在；即使本阶段不加载真实内容，也不会阻塞主流程。
- AC4: 稳定指令和动态环境信息分开注入；当前时间、工作目录和任务模式变化不会改写稳定提示内容。
- AC5: 工具描述中包含关键工具使用约束，例如读取、写入、编辑、命令执行、搜索的使用边界。
- AC6: 全局指令和工具描述都强化“优先用专用工具”“编辑前先读”“不要臆造工具结果”“遵守 workspace 边界”等规则。
- AC7: 动态补充指令以特殊标签形式进入请求上下文，不出现在用户可见的普通输入文本中。
- AC8: Plan Mode 首轮会注入完整计划约束，后续轮次按设定频率重复关键约束或使用精简提示。
- AC9: `/do` 执行模式能注入参考最近计划和工具验证相关指令。
- AC10: OpenAI 兼容协议与 Anthropic 兼容协议都能携带新的系统提示、动态补充指令、历史消息和工具描述。
- AC11: 支持缓存字段的响应会被解析为 usage 或可观测统计；不支持缓存字段的响应仍能正常工作。
- AC12: `/verbose` 或等价可观测方式能显示缓存创建、缓存读取或命中相关统计，且不会显示 API key。
- AC13: 现有 Agent Loop、多工具调用、Plan Mode、thinking 回传和 Markdown 渲染测试继续通过。
- AC14: 人工对比场景文档存在，覆盖至少六类典型场景，并说明预期行为差异。
- AC15: 本阶段没有实现项目指令文件加载、自动记忆、真实 MCP 接入或自动化评估。
- AC16: 全量单元测试和 Python 编译检查通过。
