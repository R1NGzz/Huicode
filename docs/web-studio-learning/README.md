# HuiCode 全栈实践与面试证据库

## 目的与事实边界

用户建设 Web Studio 的首要目标是提高全栈开发能力和面试竞争力。实施过程必须同步沉淀可理解、可复现、可追溯的工程记录。记录服务于理解和动手实践，不以技术名词数量或文档篇幅衡量成果。

当前状态：方案与任务已生成，本目录建立记录约定；这里不声明任何 Web 功能已经实现、任何压测已经通过或用户已经掌握某项能力。

## 实施时如何记录

每个 T 任务或紧密关联的小任务组完成时，新增一篇 `Txx-主题.md`，使用 [记录模板](./entry-template.md)。先说明用户场景和问题，再解释原理、方案选择和验证结果。普通配置改动可合并记录；重要安全、一致性和故障恢复问题单独展开。

每篇记录必须链接实际代码、测试与相关设计文档。验证证据写清命令、环境、预期、实际结果及限制；未执行的验证标为未验证。提交存在后可补充 commit，不编造提交或性能数字。不复制密钥、用户隐私和完整敏感日志。

实施中出现真实问题，当次记录症状、排查假设、证据、根因、修复和回归方法；尚未解决的如实标记。预先考虑的风险写为设计风险或故障注入场景，不能包装成真实线上事故。

每个里程碑结束时整理 `M1-review.md` 等阶段复盘：串联端到端数据流，汇总已验证成果、遗留问题、设计变化和适合面试讲述的案例，链接原始记录，不重复抄写全文。

## 每次阶段交付的沟通方式

1. 说明本阶段实现了什么，以及真实业务中为什么需要它。
2. 选取少量关键原理，结合本项目代码解释，不只列框架名。
3. 展示一个实际难点或关键取舍，以及验证依据和剩余限制。
4. 提供一个可自行运行的复现实验、一个小改动练习和两到三个自测问题，附检查方法。
   实验必须明确终端类型、工作目录、前置依赖、完整可复制命令、预期输出、失败解释及恢复步骤；先提供无需修改业务代码的入门操作，再提供进阶修改。不要用“改测试映射”等省略操作细节的描述代替教程。
5. 给出学习记录链接。练习为用户可选，不自动阻断后续实施。

## 面试材料规则

- 回答按“场景与约束 → 选择及替代方案 → 实现 → 验证 → 局限”组织。
- 区分本人实际参与、AI 辅助实现、尚未亲自复现的内容；不自动把生成代码描述为用户独立开发。
- 简历候选表述只引用已实现且已验证的结果；没有测量就不写性能提升、并发规模和可用性数字。
- 理解状态默认“待用户自测”。只有用户实际解释、修改或复现后的反馈才能记录为已练习或已掌握，不能凭代码完成替用户认定。
