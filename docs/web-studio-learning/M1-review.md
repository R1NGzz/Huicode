## 一句话结论

**M1 交出来的是一批"各自正确、但还没有连起来"的部件。** 每一样都能独立测试，
**没有一样跑过一次真实的 Agent 会话**——把它们接进 `huicode/agent.py` 是 T16（M2）。
这是 M1 最重要的边界，也是这一阶段所有"不能声称"条目的共同来源。

## 这一阶段真正踩到的坑（值得面试讲的按价值排序）

按"如果没人注意到会怎样"排序，不按任务顺序。

### 1. 事务回滚把撤销操作一起回滚了（T5）

"先吊销刷新令牌链，再抛 401"——`get_session` 把每个请求包在事务里，异常触发回滚，
于是**吊销被撤销了**。测试全绿，因为断言的是状态码。

- 教训：**在事务边界内"先写后抛"是无效的**。要写就得让事务提交，然后返回而不是抛出。

### 2. 超时之后被杀的是 `cmd.exe`，不是命令（T12）

`subprocess.run(timeout=...)` + `shell=True` 杀掉的是直接子进程。真正的命令是它的
孙子，会继续写文件，**而调用方以为已经停了**。

- 教训：**"停住了"是个需要验证的断言，不是 API 的承诺。** 验证方式是一条会自己
  写文件的孙进程 + 断言文件停止变化；并且把 `taskkill /T` 的 `/T` 去掉确认护栏会红。

### 3. `localhost` 在 Windows 上先解析成 IPv6（T8、T12）

Docker 只发布 IPv4，于是每个连接先等一次 IPv6 失败。**症状是慢，不是报错**——
集成测试 111 秒 vs 15 秒，很容易被当成"测试本来就慢"。它最初还被 `skipTest` 掩盖着：
环境不可用被当成"没跑"。

- 教训：**"慢"和"错"一样要看。** 以及：把用例挂在环境变量后面等于平时不跑。

### 4. 脱敏器两个方向都会错（T11）

规则重复施加会留下残片（`api_key=[REDACTED]]`），说明第一轮没脱干净；`(?i)` 让
`token_count=5` 被误伤。两个方向相反的 bug 出现在同一个模块里。

- 教训：**脱敏的验证必须同时断言"该脱的脱了"和"不该脱的没动"。** 只测一个方向，
  另一个方向就会在生产上出现。

### 5. 取消令牌派生出的工作仍然会被调度起来（T9）

子令牌确实是取消状态，但 `ensure_future` 还是会跑它到第一个检查点——"取消"和
"没开始"之间有一段什么都不设防的空窗。

- 教训：**"状态是对的"和"行为是对的"是两件事。**

### 6. 同一个方向错误犯了两次（T10、T12）

能力词表和执行机制都先被放进了 `huicode/server/`，导致 `huicode/tools/` 反向依赖
服务端。两次都是"敲 import 那一行时想起来的"，**没有任何测试会红**。

- 教训：**分层的正确性没有自动化兜底，只能靠每次写依赖时想一下方向。** 这条要写进
  协作约定，而不是指望记忆。

### 7. 空过的用例（T12 进程树）

孙进程从没启动时 `"" == ""` 也算通过。修法是先断言"它跑过"，再断言"它停了"。

- 教训：**写"某事不再发生"的断言前，先写"某事发生过"。**

## 现在可以说 / 不能说什么

**可以说**（都有测试证据）：

- 服务端配置、认证、租户隔离、路径解析、事件持久化与补偿、取消与预算、能力声明与
  权限判断、脱敏、受控执行边界**各自**已实现并有测试。
- 真实 PostgreSQL 上的迁移升降级往返通过；真实 Redis 上的并发事件追加通过。

**不能说**：

- ❌ "Web Studio 能跑一次对话"——**没有任何一样接进了 Agent Loop（T16）**。
- ❌ "实现了沙箱"——只有进程边界与环境过滤，没有隔离机制；路径校验不等于沙箱。
- ❌ "实时事件推送可用"——映射器与订阅器都只被测试调用过，SSE 是 T17。
- ❌ "审批流程可用"——T10 只发出了审批事件，等待与唤醒是 T14。
- ❌ "所有出口都脱敏了"——Artifact 与 Diff 还没有。
- ❌ "进程数受控"/"POSIX 上验证过"/"性能没有影响"——均无测量或未执行。
- ❌ 任何性能提升、并发规模、可用性数字——**没有测量就不写**。
